## 2. Принятые решения

| Решение | Обоснование |
|---------|-------------|
| **SSH выключен по умолчанию**, включается флагом `-ssh` | Безопасный дефолт: маячок, случайно поднятый в сети, сейчас даёт shell всем, кому CA выдал сертификат. Ломает сценарий из `docs/USAGE.md` — это ожидаемо и отражено в правке документации (фаза 4) |
| **Обмен сертификатами по mTLS включён по умолчанию** (`-auto-trust=false` для отключения) | Отдать свой сертификат может только узел, прошедший mTLS-рукопожатие, а `TLSClientConfig` проверяет CA — случайный из LAN внутрь не попадёт. Удобство важнее, компенсации ниже |
| **Обратная совместимость не нужна**, старых узлов в сети нет | Позволяет не тащить v1-пакеты, состояние `UNVERIFIED` и миграционные скрипты |
| **Пере-выдача потерянного ключа — с предупреждением**: `provision-beacon -node <cn>` заменяет запись индекса и сообщает старый серийник | Одно имя = один живой сертификат. Без предупреждения в сети остаются два валидных сертификата с одинаковым CN |
| **Отзыв по настоящему `cert.SerialNumber`**, а не по хешу от CN | Он уже случайный 128-битный (`ca.go:134`), уникален на выдачу и напрямую ложится в `x509.CreateRevocationList` |

### Компенсации для cert-share on by default

1. **Утечка roster'а.** Любой валидный узел узнаёт имена и публичные ключи остальных. Наружу уходят CN и сертификаты — не приватные ключи и не IP. Приемлемо.
2. **Подмена CN.** `provision-beacon` не проверяет уникальность имени, поэтому злоумышленник с валидным сертификатом может подсунуть cert-share с чужим CN. Компенсация: cert-share подписывается и проверяется (фаза 1), при конфликте CN с другим ключом — **отказ и громкий лог**, а не «победил первый». Легитимная пере-выдача и попытка подмены выглядят одинаково, поэтому автоматического выбора быть не должно ни в одну сторону.
3. **Cert-share расширяет круг SSH-доступа**, потому что попадает в `getTrustedCerts()` → `authorize`. Нишу закрывает решение «SSH off по умолчанию»: для доступа нужен ещё и `-ssh` с непустым `-ssh-allow`.

## 3. Фазы работ

### Фаза 0 — Модель идентичности (1.5–2 дня) — ВЫПОЛНЕНА

Блокер для всего остального: пока идентичность не согласована, подписи, gossip и
roster не имеют смысла.

1. [x] `provision-beacon` генерирует **две** пары ключей: ECDSA P-256 (TLS + SSH) и Ed25519 (discovery + подписи gossip). Обе сохраняются в `dataDir/beacon-<name>/`.
2. [x] Публичный ключ Ed25519 пишется в сертификат как SAN URI: `urn:beacon:ed25519:<base64url>`.
3. [x] **`nodeID = sha256(ed25519Pub)[:16]`** единообразно: discovery, gossip, логи, roster, монитор.
4. [x] `loadOrCreateEdKey` читает ключ с диска, отсутствие — ошибка, а не молчаливая генерация.
5. [x] `GenerateNodeID()` удалён; `SubjectKeyId` перестал использоваться как идентификатор узла.
6. [x] Появился `ca/index.json`: `CN → {serial, nodeID, issuedAt}`. Выдача отказывает в дубликате CN.
7. [x] `provision-beacon -reissue` — пере-выдача с предупреждением о старом серийнике.
8. [x] `ProtocolVersion = 2`. Announce расширен публичным ключом; пакеты v1 отбрасываются как невалидные.

**Проверено на реальных узлах:** подняты `beacon-nas` (amd64, 192.168.1.4) и
`beacon-laptop` (192.168.1.166, x86_64). Взаимное обнаружение проходит, NodeID
совпадают с выданными при выдаче, подписи принимаются, mTLS поднимается в обе
стороны. Узел с посторонним CA отвергается на этапе discovery.

#### Отклонения от плана, выявленные при реализации

1. **Архив заменённых сертификатов** (`ca/replaced/<cn>/<serial>.pem`). Пере-выдача
   перезаписывает `cert.pem`, после чего прежний сертификат исчезает с диска — но
   именно его серийник CLI показывает для отзыва, и искать его больше негде.
   Без архива предупреждение о пере-выдаче было бы бесполезным: отозвать старый
   сертификат было бы физически нечем. Пункт не был в плане, всплыл на тесте.

2. **`normalizeNodeName` проверяет длину исходного имени, до добавления префикса.**
   Иначе опечатка из двух символов молча превращалась бы в валидное `beacon-xx`,
   и пользователь не заметил бы промаха.

3. **Ключи подписей соседей берутся из сертификатов, а не из файлов
   `ed25519-key.pem`.** Для проверки подписи gossip нужен только публичный ключ,
   а он есть в SAN. Прежний вариант требовал бы раздавать соседям приватные
   ключи, что недопустимо. Проверено: `cert.pem` соседа без приватного ключа
   достаточен для регистрации ключа подписи.

4. **`beacon ssh <имя>` больше не отправляет пакеты.** Раньше probe читался по пути
   ECDSA-ключа, `loadEd25519Key` всегда падал, и announce просто не уходил. Теперь
   используется собственный Ed25519-ключ маячка и настоящий NodeID.

5. **Попутно закрыты два unreachable code** (`discovery.go`, `ssh_server.go`) —
   пункт 31 плана, сделан заранее, так как попадал в изменяемые файлы.


### Фаза 1 — Криптография (2–3 дня) — ВЫПОЛНЕНА

9. [x] Подпись discovery проверяется (сделано в фазе 0).
10. [x] `handleGossip` проверяет подпись пакета; ключи соседей регистрируются при успешном mTLS-рукопожатии с проверкой `nodeID == f(ключ из сертификата)`.
11. [x] `VerifyHostKey` проверяет host-ключ по сертификату CA, CRL и сроку. `InsecureIgnoreHostKey` удалён из клиента: нет TrustStore — ошибка, а не отключение проверки.
12. [x] CRL переведён на `crypto/x509`: подпись CA, `CRLNumber`, `ThisUpdate`/`NextUpdate`, настоящие серийники. Свой бинарный формат и `SerializeCRL` удалены.
13. [x] Автоконверт старого CRL с бэкапом `crl.pem.v1.bak`; нерезолвенные записи не теряются молча.
14. [x] `MergeGossipCRL` принимает объединение всегда, номер CRL монотонен и переживает перезапуск.

**Проверено на реальных узлах** (192.168.1.4 и 192.168.1.166): узел без CRL на диске получил CRL #1 по gossip через сеть, отзыв сохранился в локальном кэше и пережил перезапуск; отозванный узел отвергался на уровне mTLS.

#### Отклонения от плана, выявленные при реализации

1. **Проверка подписи CRL при загрузке.** План не предусматривал, но тест показал: файл CRL, подписанный посторонним CA, разбирался и его отзывы применялись. Любой, кто сумел положить файл в каталог `ca/`, мог отозвать чужие сертификаты. Теперь подпись проверяется до принятия записей.

2. **Локальный кэш отзывов (`ca/revoked-cache.json`).** Обнаружено на живых узлах: подписать CRL может только CA, поэтому принятые по gossip отзывы держались только в памяти и исчезали при перезапуске — отозванный узел возвращался в сеть после ребута соседа. Кэш не подписан CA намеренно: он пополняется только проверенными записями и читается на той же машине, как и `ca-cert.pem`.

3. **Gossip стал двусторонним.** Раньше отзывы отправлял только инициатор соединения; пир, подключившийся сам, узнавал о них лишь через 30-минутный цикл. Теперь `pushGossip` работает на обоих концах соединения.

4. **Номер CRL инкрементируется на каждый отзыв.** Без этого версии снова могли совпадать — то есть исходный дефект версий вернулся бы в новой реализации.

#### Отклонения от плана, выявленные при реализации

1. **Причина неработающего `beacon ssh <имя>` оказалась не в фильтре, а в сокете.**
   Объявление отправлялось с отдельного сокета `DialUDP`, то есть с
   эфемерного порта; сосед отвечал по адресу отправителя — на уже закрытый
   порт. Поэтому маячок видел announce, отвечал, а клиент упирался в «не
   ответил в сети». Отправка и приём теперь идут одним сокетом.

2. **Ответ discovery проверяется подписью из сертификата, а не только
   NodeID.** Прежняя проверка «NodeID пакета == искомый» была пустой:
   идентификатор записывается в пакет отправителем и подделывается без
   ключа. Теперь подпись сверяется публичным ключом из сертификата целевого
   узла — тем же ключом, что и в `Discovery.verifyPacketSignature`.

3. **Несколько адресов на один NodeID — ошибка, а не выбор первого.** Раньше
   под неоднозначностью подразумевался один адрес в карте. Клон или подмена
   дают два ответа на один NodeID, и выбор был бы произвольным, поэтому
   подключение отменяется с перечислением кандидатов.

4. **Discovery маячка больше не наследует `-bind`.** Сокет, привязанный к
   одному адресу (`-bind 192.168.1.166`), не получает broadcast-пакеты — они
   доставляются только сокетам, слушающим все адреса. С `-bind` на конкретный
   адрес маячок не видел бы соседей вовсе. Адрес `-bind` продолжает
   применяться к TCP-слушателям TLS и SSH. Добавлено отдельное поле
   `Config.DiscoveryBindAddr` (пусто = `0.0.0.0`).

5. **`state.json` пишется при любом запуске маячка, а не только с `-tui`.**
   Иначе отдельный процесс `beacon monitor` не видел бы адресов: файл
   появлялся только у того же процесса, который и так знает пиров в памяти.

6. **Список пиров в TUI обновляется на каждом тике.** Раньше он собирался один
   раз при старте, из-за чего сосед, появившийся позже, не отображался никогда,
   а адрес — тем более. Добавлен `mergePeers`, сохраняющий статусы оставшихся
   пиров и сбрасывающий их при смене адреса.

7. **`beacon monitor -tls-port`.** Монитор пинговал соседей на 1985, даже
   когда маячок запущен на другом порту, и показывал живых соседей офлайн.

8. **Узел больше не может записать себя в список пиров.** Клиент `beacon ssh`
   на той же машине объявляется по discovery, маячок дозванивается до
   собственного TLS-порта и видит собственный сертификат — в `state.json`
   появлялся сам маячок. Отказ на трёх точках: `onPeerDiscovered`,
   `handleIncomingConnection`, `JSONState`.

9. **SSH-доступ требует сертификат роли `server` — это решение фазы 2, а не
   ошибка.** Выяснилось при первой же сквозной проверке `beacon ssh`: узел с
   ролью `peer` отвергается на авторизации. Критерий готовности «узел с
   `CN=client` не может авторизоваться по SSH» выполняется, поэтому в тестах
   клиент выпускается ролью `server`, а отказ роли `peer` закреплён отдельным
   тестом.

10. **Шифрование ключей не включается принудительно.** Пункт плана говорил
    «ключ CA шифруется по умолчанию», но без секрета шифровать нечем, а
    спрашивать пароль в неинтерактивном скрипте — значит зависать. Поэтому
    секрет задаётся явно (`-passphrase-file`/`BEACON_PASSPHRASE`), а без него
    `generate-ca` печатает предупреждение, что ключ лежит открытым. Всё
    выпущенное ранее перешифровывается при первом чтении с секретом.

11. **`tls.LoadX509KeyPair` не понимает нестандартный PEM-блок** и отвергал
    файл целиком. Загрузка сертификата узла теперь собирается вручную из
    расшифрованного ключа (`LoadNodeCertificate`).
