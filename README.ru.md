# Сетевые Маячки (Network Beacons)

> **Проект создан при участии ИИ-агентов.** Практически весь код, тесты и
> документация написаны ИИ-агентами (OpenCode/Claude) под управлением человека
> [@mnnoee](https://github.com/mnnoee). Человек принимал архитектурные решения,
> проверял работу на живых устройствах и отвечал за всё, что здесь есть. Имейте
> в виду: код написан быстро и пересмотрен человеком, а не формальным аудитом.

Обнаружение устройств в локальной сети с шифрованным обменом и SSH-доступом по
списку разрешённых. Один бинарник, ноль внешних зависимостей в рантайме.

```
маячок  ──UDP broadcast──►  маячок
   │                            │
   └───── mTLS + cert-share ────┘   отзывы расходятся тем же каналом
```

## Что это делает

Устройства в одной сети находят друг друга по UDP broadcast и аутентифицируются
взаимным TLS с общим корневым сертификатом. После этого каждый знает сертификат
соседа, может обращаться к нему по имени и получает от него обновления списка
отозванных сертификатов.

- **Никаких DNS, серверов и облаков.** Всё внутри вашей сети.
- **Отзыв работает.** Отозванный узел отвергается на mTLS и SSH, а соседи узнают
  об отзыве без обращения к CA-машине.
- **SSH по имени:** `beacon ssh beacon-nas uptime` — имя разрешается в адрес
  через тот же discovery.
- **Монитор в терминале:** список соседей, адреса, пинг, статус.

## Для чего это нужно

Сеть из домашних или офисных устройств — роутеров, NAS, Raspberry Pi, старых
телефонов — где обычно есть выбор между «просто пустить всех по SSH» и «никого
не пускать». Здесь узел пускает только тех, кому администратор выдал сертификат,
а отзыв действует без перезагрузки и без ручного обхода.

Типовые сценарии: доступ к NAS, когда роутер не имеет нормального SSH; сеть из
пяти-двадцати устройств, где не хочется ни править sshd на каждом, ни держать
один общий пароль; эксперименты с криптографией и распределёнными системами —
проект небольшой и весь в одном файле на Go.

## ⚠️ Где это работает и где не работает

**Только локальная или недоверенная сеть — и то не всякая.**

| Подходит | Не подходит |
|----------|-------------|
| Домашний LAN, своя подсеть | Интернет без дополнительного туннеля или VPN |
| Изолированная сеть в офисе, на даче | Сеть, где вы не контролируете, кто в неё входит |
| Лабораторный стенд, pet-проект | Сеть с чужими устройствами и без изоляции |

Почему так:

- **Обнаружение — широковещательное.** Любой в вашей сети видит UDP-пакеты
  маячков. Само по себе это почти ничего не даёт (пакеты подписаны и проверяются),
  но количество видимой информации стоит понимать.
- **Компрометация CA-машины = компрометация сети.** Ключ CA не защищён HSM и
  лежит на диске (шифруется AES-256-GCM, если задан секрет, — но секрет тоже
  нужно где-то хранить).
- **Отзыв требует, чтобы узлы узнали о нём.** Узлы обмениваются CRL по gossip;
  если узел изолирован от сети, отзыв к нему не дойдёт.
- **Время в протоколе.** Часы узлов должны отличаться не больше чем на 5 минут.
- **Защита от MITM — только от вашей сети.** В сети, где есть активный
  наблюдатель вне вашего контроля, модель «мы доверяем только выданным CA
  сертификатам» не работает: тот, кто может подменить сертификат при выдаче,
  контролирует сеть.

Проект не проходит аудит и не позиционируется как готовое решение для
продакшена. Это рабочий инструмент для своей сети и полигон для экспериментов.

## Быстрый старт

Нужен Go 1.26+.

```bash
git clone https://github.com/mnnoee/beacon.git
cd beacon
go build -o beacon .
```

### CA-машина

```bash
./beacon ca generate-ca -dir ./data                 # ключ и сертификат CA
./beacon ca provision-beacon -dir ./data nas         # узел для сети
./beacon ca provision-beacon -dir ./data -role server nas   # узел, раздающий SSH
```

Роль `server` нужна только узлам, с которых будут подключаться по SSH: SSH-доступ
получают исключительно сертификаты этой роли.

### Узел

```bash
# файлы маячка и сертификат CA кладём на устройство
scp -r ./data/beacon-nas nas:~/beacon-data/
scp ./data/ca/ca-cert.pem        nas:~/beacon-data/ca/

./beacon beacon -dir ~/beacon-data -name beacon-nas \
  -broadcast 192.168.1.255 -ssh -ssh-allow beacon-nas,beacon-other
```

SSH-сервер **выключен по умолчанию**: пустой `-ssh-allow` означает отказ всем,
кроме самого узла.

### Что дальше

```bash
# соседи, кто с кем соединился
cat ~/beacon-data/state.json

# подключение к соседу по имени
./beacon ssh -dir ~/beacon-data -name beacon-nas \
  -disc-port 1984 -broadcast 192.168.1.255 beacon-other 'uptime'

# монитор (отдельный процесс, читает state.json)
./beacon monitor -dir ~/beacon-data -name beacon-nas -tls-port 1985

# отзыв узла: подписан CA, расходится по gossip
./beacon ca revoke-beacon -dir ./data -node beacon-other
```

Подробности: [docs/USAGE.md](docs/USAGE.md) — команды и флаги,
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) — как устроено доверие.

## Как это устроено коротко

| Слой | Решение |
|------|---------|
| Обнаружение | UDP broadcast, каждый пакет подписан Ed25519-ключом узла |
| Идентичность | `nodeID = sha256(Ed25519-ключ)[:16]`, ключ лежит в SAN сертификата |
| Транспорт | Mutual TLS, клиентский сертификат обязателен |
| Обмен сертификатами | `PktCertShare` поверх установленного mTLS |
| Отзывы | CRL на `crypto/x509`, распространение по gossip, локальный кэш на узлах без ключа CA |
| Ключи на диске | Права 0600, опционально AES-256-GCM с секретом из `BEACON_PASSPHRASE` |

Протокол версии 2. Взгляд на доверие и на угрозы — в
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
